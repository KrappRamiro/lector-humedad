## Claims

- Today `MoistureSensor::read` returns `u8` and `sensor_display` hands it to the display: `src/moisture_sensor.rs` (`pub fn read(&mut self) -> anyhow::Result<u8>`), `src/main.rs` (`sensor_display`).
- Plan Task 3 asks for `Value`, `Reading`, `Gauge` in `fak-core/src/gauge.rs`, with the three tests, and commit message `feat(core): add Value, Reading and Gauge`: plan, Task 3.
- Payload is a JSON number or boolean, arriving in Chapter 8: plan Task 8 payload table (`{"value":42,...}`, `{"value":true,...}`).
- `match` must be exhaustive: E0004 reproduction above.
- Spec doc comment on `Value` ("Adding a kind here makes the compiler flag every `match` that needs updating"): spec section 4, `gauge.rs`.
- Plan Task 8 asks for no wildcard arm: plan Task 8, Step 3 ("matches on `Value` (no wildcard arm, so a new variant forces an update)").
- `i32` matches the chip's native word; ESP32-C3 is 32-bit RISC-V: spec section 4 design notes ("`Integer(i32)` matches the chip's native word size"); target `riscv32imc-esp-espidf` in `.cargo/config.toml`.
- Plan forbids silent `as` casts, widen with `From`: plan Global Constraints.
- `u32` source needs `i32::try_from` because a `u32` can exceed `i32::MAX`: spec section 4 design notes.
- `From` gives `Into` through a blanket impl: Rust standard library docs, `std::convert::From` ("implementing From automatically provides one with an implementation of Into thanks to the blanket implementation in the standard library"), https://doc.rust-lang.org/std/convert/trait.From.html. Behavior confirmed by `percent.into()` compiling in `dyn_ok.rs`.
- `ts` is Unix seconds taken when the hardware was read: spec doc comment on `Reading::ts`.
- A subscriber reads the broker's retained message and needs its age: spec section 1, "In scope" (`readings/<reading-id>` ... "retained, with a 180-second `messageExpiry`").
- `42_u8` pins the test to `From<u8>`; with one integer impl a bare `42` compiles (reviewer's check, rustc nightly 2026-09-15); with a second impl `From<u16>` the literal falls back to `i32` and fails: `lit2.rs` in scratchpad `ch2/`, output "error[E0277]: the trait bound `Value: From<i32>` is not satisfied". Status: failed, as intended (described in the chapter, not shown as a listing).
- `255 as i8` is `-1`: Rust reference, "Numeric cast" (casting between integers of the same size is a no-op, two's complement reinterpretation), https://doc.rust-lang.org/reference/expressions/operator-expr.html#numeric-cast .
- `Eq` adds reflexivity (every value equals itself); NaN is not equal to itself: `std::cmp::Eq` docs (equivalence relation, "reflexive: a == a"), https://doc.rust-lang.org/std/cmp/trait.Eq.html ; `f32`/`f64` implement only `PartialEq` for that reason (same page).
- Blanket impl of `Into` for every `From` pair: `impl<T, U> Into<U> for T where U: From<T>`, std docs for `Into`, https://doc.rust-lang.org/std/convert/trait.Into.html .
- `&'static str` literal lives for the whole run of the program: Rust Book ch. 10.3, "The Static Lifetime" ("All string literals have the 'static lifetime").
- Publisher runs once a minute: plan Task 13 (`Ticker::every(60 s)`).
- Until SNTP, `ts` counts from 1970 at boot, which the plan accepts: plan Task 5, Step 2.
- `assert_eq!` needs `PartialEq` and `Debug`: standard library docs for `assert_eq!` ("Like assert!, this macro has a second form... uses Debug"); confirmed by the tests compiling with those derives.
- `Copy` allowed only when every field is `Copy` (and a type that owns heap data via `Drop` can't be `Copy`): Rust reference / `std::marker::Copy` docs ("A type can implement Copy if all of its components implement Copy"), https://doc.rust-lang.org/std/marker/trait.Copy.html.
- Prometheus gauge definition, quoted: https://prometheus.io/docs/concepts/metric_types/ , "A gauge is a metric that represents a single numerical value that can arbitrarily go up and down." Fetched 2026-11-04.
- Spec takes the term from metrics systems like Prometheus; sensor owns hardware and writes, gauge is the shared latest value; a chip measuring two things is one sensor writing several gauges: spec section 4, "Sensors and gauges".
- `reading_id` like `"moisture-01"` becomes the last topic segment: plan Task 8 (`reading_topic(.., "moisture-01")` gives `.../readings/moisture-01`).
- `None` until first successful read or after a failed one: spec doc comment on `Gauge::latest`. Display shows dashes for `None`: plan Task 4 (`no_reading_shows_dashes`) and Task 5 Step 4.
- Gauges know nothing about MQTT or JSON: spec section 4 design notes, first bullet.
- Generics monomorphize; array elements share one type; `&dyn Gauge` erases the concrete type: Rust Book ch. 18 "Using Trait Objects That Allow for Values of Different Types" (https://doc.rust-lang.org/book/ch18-02-trait-objects.html); array behavior confirmed by Figure 2-2 and Figure 2-3 samples.
- vtable: a table of function pointers built per implementing type; a `&dyn` call looks the method up at run time, which costs more than static dispatch: Rust Book ch. 18.2 "Trait Objects Perform Dynamic Dispatch" (https://doc.rust-lang.org/book/ch18-02-trait-objects.html, "there is a runtime cost when this lookup happens that doesn't occur with static dispatch"); Rust reference, "Trait objects" (pointer to the value plus pointer to a vtable).
- `[&dyn Gauge; 2]` annotation is what coerces `&Moisture`/`&Door` to trait objects; without it the array takes the first element's type: `noann.rs` above.
- String literals are compiled into the binary and never freed: Rust Book ch. 4.1 ("string literals ... hardcoded directly into the final executable"), and ch. 10.3 'static.
- Associated type is a placeholder each impl fills in: Rust Book ch. 20.2, same section as the `Counter` sample.
- ESP32-C3 pointers are 4 bytes, so `&T` is 4 and `&dyn Gauge` is 8 there: `rustc --print cfg --target riscv32imc-unknown-none-elf` gives `target_pointer_width="32"` (same riscv32imc ISA as the project's `riscv32imc-esp-espidf`); two-pointer layout from the Rust reference, "Trait objects".
- Retained message: the broker keeps the last message per topic and delivers it to later subscribers: MQTT 5.0 spec, section 3.3.1.3 RETAIN; spec section 1 (retained readings).
- `HashMap` keys must implement `Eq` and `Hash`: std docs for `std::collections::HashMap` ("It is required that the keys implement the Eq and Hash traits").
- `Clone` is a supertrait of `Copy`: std docs, `pub trait Copy: Clone`.
- `i32::try_from` returns a `Result`: std `TryFrom` docs.
- `MoistureSensor::read` signature `anyhow::Result<u8>`: `src/moisture_sensor.rs`.
- Trait object is two pointers (data + vtable); 8 vs 16 bytes on the development machine: `size.rs` printed "&M = 8, &dyn Gauge = 16, usize = 8" (x86_64 host); Rust reference, "Trait objects" / pointer layout of `dyn` references.

- Associated type rejected because `[&dyn Trait; N]` fails with E0191; other alternatives (gauge writing its own output, `serde` + `erased-serde`, visitor) and the reasons: spec section 4 design notes, last bullet. E0271 for the specified variant: `assoc2.rs` reproduction above.
