Values and gauges

Today the moisture percentage travels a short road. MoistureSensor::read produces a u8 (inside an anyhow::Result), and sensor_display hands that u8 straight to the display. The only code that ever sees a reading is code that already knows it came from a moisture sensor.

That stops being true once the board publishes over MQTT. The publisher has to send every reading on the board, and it should do so without knowing what a moisture sensor is. So the question for this chapter is a narrow one: what does the rest of the firmware need to know about a reading, and nothing more?

We answer it in three pieces, the same three that plan Task 3 asks for. First, the value itself, as a type that admits only the kinds of value we can publish. Second, the reading, which pairs that value with the moment it was taken. Third, the gauge, a trait that any source of readings can implement.

All three live in a new file, fak-core/src/gauge.rs, because none of them touches the hardware. That puts them on the host side of the split from Chapter 1, where cargo test-core can test them in seconds.

A closed set of values

A reading on the wire is a JSON number or a JSON boolean (the payload format arrives in Chapter 8), and the type that holds it should say so. An enum with one variant per kind does exactly that:

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Value {
    Integer(i32),
    Bool(bool),
}

A Value is either an Integer carrying an i32 or a Bool carrying a bool, and nothing else. We call an enum like this one closed, because the compiler knows every variant it can hold.

That knowledge is what makes a match on it trustworthy. A match in Rust must be exhaustive: every variant needs an arm, or the code doesn't compile. For example, if a later sensor added a Text variant, a function that matched only on Integer and Bool would stop compiling with this error:

error[E0004]: non-exhaustive patterns: `Value::Text(_)` not covered

Think of a customs form that lists every category of goods a port accepts. When the port starts accepting a new category, every form in circulation needs a new box, and an exhaustive match is the clerk who refuses a form without it.

The spec writes this promise into the doc comment of Value: "adding a kind here makes the compiler flag every match that needs updating".

The promise holds only as long as nobody writes a wildcard arm (_ => ...). A wildcard accepts any variant it hasn't seen, including the new one, and the clerk waves the form through. That is why plan Task 8 asks for the payload code to match on Value with no wildcard.

The integer variant holds an i32, which is the native word of the ESP32-C3, a 32-bit RISC-V core. It is signed because some future quantity (a temperature, say) can go below zero, even though moisture never does.

Conversions with From

The moisture sensor produces a u8, and the gauge needs a Value, so somewhere a u8 has to become a Value::Integer. Rust's convention for a conversion that can't fail is the From trait:

impl From<u8> for Value {
    fn from(v: u8) -> Self {
        Value::Integer(i32::from(v))
    }
}

Inside the impl, i32::from(v) widens the u8 into an i32. The standard library offers that conversion only because every u8 fits in an i32, so its existence is itself a guarantee.

An as cast gives no such guarantee. It compiles even when the value doesn't fit, and it quietly produces a different number: 255_u8 as i8 is -1. That is why the plan's global constraints forbid a silent as and ask for From.

A u32 has no From into i32, because a u32 can exceed i32::MAX. A sensor that produced one would use i32::try_from, which returns a Result, and the spec leaves that impl unwritten until some sensor needs it.

Writing From also gives us Into for free, through this impl in the standard library:

impl<T, U> Into<U> for T
where
    U: From<T>,

An impl like this one, written once for every type that meets a condition, is called a blanket impl. This one reads as "any T can turn into any U that knows how to be made from a T". Our From<u8> for Value meets that condition, so u8 gains .into() toward Value without another line from us.

A call to .into() needs the compiler to know the target type, because a u8 could turn into many things. A type annotation is enough context. For example, let v: Value = percent.into(); compiles, and the compiler picks From<u8> for Value on its own because the annotation names the target.

From<bool> follows the same shape, wrapping the bool in Value::Bool, and needs no widening at all.

A reading

A value on its own says how wet the soil is, but not when. The broker keeps the last message on each topic (a retained message) and hands it to anyone who subscribes later, possibly long after it was sent. That subscriber needs to know how old the value is, so the plan pairs the two in a struct:

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Reading {
    pub value: Value,
    /// Unix seconds, taken when the hardware was read.
    pub ts: u64,
}

The timestamp is taken when the hardware is read (not when the reading is published). The publisher runs once a minute, so a reading may wait up to a minute before it leaves the board. The timestamp records the moment the soil was measured, whatever happens to the reading afterward.

A struct field with a declared type also gives .into() its target, so the firmware can write Reading { value: percent.into(), ts } and the compiler picks From<u8> for Value from the type of value.

Until the board syncs its clock in Chapter 11, those seconds count from 1970 at boot. The plan accepts that for now, because nothing reads the timestamp before the clock is set.

What each derive buys

Both types carry the same five derives, and each one is there for a reason we can name.

Debug and PartialEq serve the tests. assert_eq! compares its two sides with PartialEq, and when they differ it prints both with Debug, so the test failure shows us what came out.

Eq adds one promise on top of PartialEq: every value equals itself. Floats can't make that promise, because NaN is a float that isn't equal to itself. Neither Value nor Reading contains a float, so both can make it. Nothing in this task uses Eq yet. We derive it because the types can honestly make the promise, and some standard collections require it, such as HashMap, whose keys must implement Eq and Hash.

Copy lets a Reading be duplicated by copying its bits, and Clone is the trait that Copy builds on, so the two are derived together. Rust allows Copy only when every field is itself Copy, and a Reading qualifies because Value (an i32 or a bool) and u64 both are.

A reading is small, so passing copies around is cheap, and no code ever has to borrow one from somewhere else.

The gauge

The last piece is the one the publisher and the display will hold, and it borrows its name from metrics systems. Prometheus defines a gauge as "a metric that represents a single numerical value that can arbitrarily go up and down". The spec takes the word for the latest value of one measured quantity, overwritten by the code that reads the hardware and read by everyone else. Our gauges stretch the word a little, since a gauge here may also hold a bool.

That gives the project two words with two jobs. A sensor owns hardware and writes. A gauge is what the sensor writes into. For example, a chip that measures temperature and humidity would be one sensor writing two gauges.

The trait states what every gauge offers:

pub trait Gauge {
    fn reading_id(&self) -> &'static str;
    /// `None` until the first successful read, or after a failed one.
    fn latest(&self) -> Option<Reading>;
}

reading_id names the quantity, such as "moisture-01". In Chapter 8 it becomes the last segment of the MQTT topic.

The return type &'static str is a borrowed string that lives for the whole run of the program. A string literal like "moisture-01" has that lifetime, because it is compiled into the firmware image and never freed. The name is fixed at build time, so nothing about it needs to be owned or allocated.

latest returns an Option, and its None carries meaning: no successful read yet, or the last read failed. The display will show that case as dashes in Chapter 3.

Neither method knows about MQTT or JSON. A gauge hands out plain domain data, and turning that data into bytes on the wire stays the job of the code that sends it.

Trait objects

The publisher needs every gauge on the board in one list. Rust has two ways to write a function that accepts "any gauge", and only one of them can build that list.

The first is generics:

fn publish<G: Gauge>(gauge: &G) { ... }

To have two kinds side by side, picture a second gauge we don't have: a door sensor that reports open or closed as a bool. The compiler writes a separate copy of publish for each concrete type it is called with, one for Moisture and one for Door. Each copy knows exactly what it holds, which makes the call fast. What generics can't give us is the list, because every element of an array has to share one type, and &Moisture and &Door are two types.

The second way is a trait object, written &dyn Gauge. A trait object is a way of seeing a value through its trait alone, the concrete type forgotten and only its Gauge methods kept. References to different types all become the same type, &dyn Gauge, and the list becomes possible.

Forgetting the type raises a question: when the publisher calls gauge.latest(), how does it find the right latest? The answer is a small table of function pointers, called a vtable, which the compiler builds once for each type that implements the trait. A &dyn Gauge carries a pointer to that table next to the pointer to the data, as Figure 2-1 draws.

Each element of the array has the same shape whatever sits behind it: two pointers. That shape is visible in the sizes. On the development machine, a &Moisture measures 8 bytes and a &dyn Gauge measures 16, one pointer for the data and one for the vtable. On the ESP32-C3, where a pointer is 4 bytes, the same two references measure 4 and 8.

A call through a trait object follows the second pointer to the table, finds latest there, and calls it with the first pointer as self. That lookup happens at run time, so it costs a little more than a generic call, where the compiler already knew which function to call. For a publisher that sends once a minute, the difference doesn't matter.

Figure 2-2 puts two unrelated gauges in one array and loops over it. This is the shape that Chapter 14 gives the publisher.

The type annotation [&dyn Gauge; 2] is what turns &Moisture and &Door into trait objects. Without it the compiler gives the array the type of its first element, &Moisture, and rejects &Door with a type mismatch. Inside the loop, both calls go through the vtables, and each gauge answers with its own value kind wrapped in the same Reading.

Associated types

The design has one obvious alternative, and to see why the spec rejected it we first need the feature it would use. The standard library's Iterator trait is the clearest example:

pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}

The line type Item; declares an associated type: a blank in the trait that each implementation fills in with a concrete type. Self::Item in the signature of next refers to whatever that blank holds.

An implementation fills the blank in with one line:

struct Counter {
    count: u32,
}

impl Iterator for Counter {
    type Item = u32;
    fn next(&mut self) -> Option<Self::Item> {
        if self.count < 3 {
            self.count += 1;
            Some(self.count)
        } else {
            None
        }
    }
}

type Item = u32; fixes the blank for Counter, so its next returns Option<u32>. Another iterator could say type Item = char; and return characters. The trait is the same, and each implementation picks the type of what it hands out.

A gauge trait could work the same way:

pub trait Gauge {
    type Value;
    fn reading_id(&self) -> &'static str;
    fn latest(&self) -> Option<Self::Value>;
}

impl Gauge for Moisture {
    type Value = u8;
    fn reading_id(&self) -> &'static str { "moisture-01" }
    fn latest(&self) -> Option<u8> { Some(42) }
}

impl Gauge for Door {
    type Value = bool;
    fn reading_id(&self) -> &'static str { "door-01" }
    fn latest(&self) -> Option<bool> { Some(true) }
}

Each gauge fills the blank with its own type, the moisture gauge with u8 and the door gauge with bool. That looks tidier than our design (no enum, no conversions), and each gauge on its own compiles and works.

Why the gauge has no associated type

The trouble shows up at the array. Figure 2-3 tries to build it in the two ways available, and both fail.

The first error comes from the type of the trait object. Code that calls latest through a &dyn Gauge has to know the type of what comes back. With the blank left open, dyn Gauge doesn't say, so the compiler demands that we fill it in, and that is E0191.

Filling it in fixes the first error and causes the second. dyn Gauge<Value = u8> and dyn Gauge<Value = bool> are two different types, and an array holds only one. The door gauge returns a bool, so it doesn't fit in an array of u8 gauges, and that is E0271.

Our Value enum moves the variety inside one type. Every gauge returns the same Option<Reading>, so every &dyn Gauge has the same type, and they all fit in one list. The price is the enum and its From impls, which is small next to a publisher that can't hold its gauges.

The spec considered three other designs and rejected each with a reason. A gauge that wrote its own JSON would leak the wire format into every gauge. serde, Rust's usual serialization library, together with erased-serde to make it work through trait objects, would add two dependencies, and "serializable" says nothing about the value's shape. A visitor, where each gauge calls back into the publisher with its concrete value, would add indirection for no gain at this size.

We know the shapes already, since the sections above built each one, so the work is in the order. The tests come first and name a type that doesn't exist yet, which means the first run fails at compile time rather than at an assertion.

That failure is still useful. It proves the tests are wired into cargo test-core, which is only true once lib.rs declares pub mod gauge;. A file that no module declares is never compiled, and its tests would pass by never running.

The test for 255 checks the top of the u8 range. That is where a careless conversion goes wrong: a cast to i8, for example, turns 255 into -1.

Finally, fak-core holds public items to clippy's pedantic lints from the start, so we run clippy-pedantic as well as the gate.

Solution

fak-core/src/lib.rs gains one line:

#![forbid(unsafe_code)]
pub mod gauge;
pub mod moisture;

pub mod gauge; tells the compiler to read gauge.rs. The pub makes its public items reachable as fak_core::gauge::... from the firmware crate.

The tests go at the bottom of fak-core/src/gauge.rs:

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn u8_becomes_integer() {
        assert_eq!(Value::from(42_u8), Value::Integer(42));
    }

    #[test]
    fn largest_u8_becomes_integer() {
        assert_eq!(Value::from(255_u8), Value::Integer(255));
    }

    #[test]
    fn bool_becomes_bool() {
        assert_eq!(Value::from(true), Value::Bool(true));
    }
}

#[cfg(test)] compiles the module only for cargo test, so none of this reaches the firmware.

use super::*; brings the parent module's items into scope, which is how the tests see Value.

Each #[test] function is one case from the plan, and assert_eq! compares with PartialEq and prints both sides with Debug if they differ.

42_u8 uses a type suffix to pin the test to the From<u8> impl it means to test. With only one integer impl a bare 42 would also compile. Once a From<u16> joins it, though, the compiler can't choose, falls back to i32 for the literal, and fails with the trait bound `Value: From<i32>` is not satisfied.

Above the tests goes the implementation, which is the spec's code:

/// One of a small, closed set of value kinds. Adding a kind here makes the
/// compiler flag every `match` that needs updating.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Value {
    Integer(i32),
    Bool(bool),
}

impl From<u8> for Value {
    fn from(v: u8) -> Self {
        Value::Integer(i32::from(v))
    }
}

impl From<bool> for Value {
    fn from(v: bool) -> Self {
        Value::Bool(v)
    }
}

/// Exactly one message on `readings/<reading-id>`.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Reading {
    pub value: Value,
    /// Unix seconds, taken when the hardware was read.
    pub ts: u64,
}

/// The latest value of one measured quantity, published as
/// `readings/<reading-id>`.
pub trait Gauge {
    fn reading_id(&self) -> &'static str;
    /// `None` until the first successful read, or after a failed one.
    fn latest(&self) -> Option<Reading>;
}

The doc comment on Value records the promise its exhaustiveness makes. #[derive(Debug, Clone, Copy, PartialEq, Eq)] gives the tests their comparison and printing, and lets a Value be copied. pub enum Value lists the two kinds, Integer(i32) and Bool(bool), each carrying its payload.

impl From<u8> for Value opens the conversion, and fn from(v: u8) -> Self is its one required method. Value::Integer(i32::from(v)) widens without loss and wraps the result.

impl From<bool> for Value repeats the shape, and Value::Bool(v) wraps the bool as it is.

The doc comment on Reading ties it to exactly one MQTT message. The same derives apply, possible because Value and u64 are both Copy.

pub value: Value and pub ts: u64 are public fields, so the firmware can build a Reading with a struct literal. The doc comment on ts fixes its unit and the moment it's taken.

The doc comment above the trait says what a gauge is to the rest of the firmware and names the topic it ends up on. pub trait Gauge declares the trait, with no associated type for the reasons in Figure 2-3.

fn reading_id(&self) -> &'static str; and fn latest(&self) -> Option<Reading>; end in semicolons because a trait only declares them, and every implementor writes the body. Both take &self, so a shared reference is enough to call them. Chapter 4 relies on that when the sensor and the display share one gauge.

How to verify

With only the tests and the lib.rs line written, run cargo test-core. It fails to compile with several lines of error[E0433]: cannot find type `Value` in this scope, one per use, and a warning about the unused use super::*;.

After the implementation, the same command reports test result: ok. 12 passed for the unit tests (the nine calibration tests plus our three) and 1 passed for the doc-test.

Then run the gate, devenv test --no-tui. A pass prints the same test summary and no clippy warnings, and it ends with Finished `release` profile and an exit code of 0. Along the way it shows one warning: linker stderr: [ldproxy] Running ldproxy, which the release build of this project always prints and which is harmless.

Finally run clippy-pedantic, which reports no warnings for gauge.rs. After /code-review on the diff, commit with feat(core): add Value, Reading and Gauge and tick the five steps of Task 3 in the plan.

What to improve

No test covers a negative Integer yet, because nothing in this task produces one. The first code that does is the payload formatting in Chapter 8, where the test negative_integer_reading_payload checks that Integer(-5) becomes "value":-5. The gap closes there, at the point where a sign could actually be lost.

reading_id also has no doc comment. A line saying it must be unique per board would help whoever adds the second gauge, because two gauges with the same id would overwrite each other's topic.
