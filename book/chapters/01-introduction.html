Introduction

A soil moisture sensor tells nobody anything until something reads it, and the station this book follows already does that much. An ESP32-C3 Super Mini reads a capacitive sensor on GPIO0 through its ADC, turns the millivolts into a percentage, and draws the percentage on a four-digit TM1637 display, all from one loop in main.rs that comes around every 100 milliseconds. What the station can't do yet is tell anyone who isn't standing in front of it. This book takes it from that loop to a board that joins WiFi, sets its clock, and publishes its reading to the fak MQTT broker every 60 seconds, announcing itself when it comes online and leaving a last message with the broker for the moment it goes away.

The route is already drawn. It lives in the implementation plan, docs/superpowers/plans/2026-10-17-mqtt-integration.md, and behind the plan sits its design, docs/superpowers/specs/2026-10-15-mqtt-integration-design.md, approved on 2026-10-17 after three independent reviews (and two more on later additions). The plan breaks the work into thirteen tasks, of which the first two are done, so this book starts at Task 3 and gives every task after it a chapter of its own (two chapters, for the two tasks that carry the most concurrency). Where a chapter and the spec ever disagree, we follow the spec and correct the chapter, because the spec is the document that went through review.

Two crates

The first thing to notice in the repository is that it holds two crates, and the reason for that goes back to a discovery about tests. Until October 2026 the project's unit tests had never run, and the workspace split spec opens its statement of the problem with exactly that sentence. The firmware binary sets harness = false in Cargo.toml, which strips every #[test] function out of the build, and .cargo/config.toml sets the runner to espflash flash --monitor, which turns cargo test into flashing the board and running the ordinary main(). Neither setting is a mistake (the first keeps rust-analyzer quiet, the second is how firmware gets onto the chip), but together they left the tests compiled into nothing.

The fix was to give logic that never touches the hardware a crate of its own, fak-core, which treats that part of the firmware as ordinary Rust: code that builds for the development machine and runs its tests there in a fraction of a second, all without a board on the desk. A cargo alias in .cargo/config.toml points those tests at the host target:

[alias]
test-core = "test -p fak-core --target x86_64-unknown-linux-gnu"

The alias exists because the whole workspace builds for riscv32imc-esp-espidf by default, and a test binary for that target can't run on a laptop. Naming the host target for one package, and only that package, is what lets cargo test-core run the nine unit tests and one doc-test in fak-core today without dragging ESP-IDF into the build.

Deciding what goes into fak-core follows one rule, which we settled on during the split: move decisions, not stateful structs. For example, the arithmetic that turns millivolts into a percentage is a decision, and it lives in fak_core::moisture. The gauge that remembers the latest reading (it arrives in Chapter 4) is state, and it stays in the firmware next to the sensor that writes to it, where module privacy can guarantee that nothing else writes to it.

The percentage math has already made that trip once. On 2026-10-20 it moved into fak-core as a loose function, percent_moisture_from_reading(raw_reading, dry_reading, wet_reading), taking three u16 values, with nothing to stop a caller from passing the dry and wet limits in the wrong order. On 2026-11-04 it became Calibration, whose const fn new refuses a dry reading that isn't above the wet one. Because the firmware builds its calibration in a const, that refusal happens during compilation, and an inverted calibration stops the build with error E0080 before any code reaches the board. Task 2 of the plan, the last one finished before this book, was exactly that change.

Where the station is going

The finished firmware runs four loops at once, and Figure 1-1 shows them next to the one thread that talks to the broker. The four loops (the moisture sensor, the display, the WiFi monitor, and the publisher) take turns on a single thread. Each loop does a little work, then pauses (to wait 500 milliseconds, say), and while it waits another loop gets the thread. The piece that hands the thread around we call the executor: one thread that resumes each loop in turn whenever the one running pauses, all four sharing it without ever running at the same instant. In this firmware the executor is a single call, block_on(select_array(..)), and the mechanics behind those two names (async functions, futures, and why each loop gets boxed before it fits in an array) are the subject of Chapter 5.

One property of that call matters already. select_array finishes as soon as any one loop finishes, and since every loop is meant to run forever, a finished loop is a bug, so the firmware turns it into an error that names the loop and restarts the board.

The MQTT client sits apart on a thread of its own, and the reason is a lock. While esp-mqtt reconnects to the broker, it holds the client's API lock through DNS, the TCP connection, and the wait for the broker's answer, and every client call made in the meantime waits for that lock. If the executor made those calls, a reconnect would freeze the sensor and the display along with it, because a call that waits on the executor's only thread stops all four loops. On a dedicated thread, fed through a bounded channel of eight requests, only that thread waits. The spec argues this in detail in its section 3, and Chapter 12 builds the threading vocabulary it needs, from std::thread to Send, before Chapter 13 writes the thread itself.

The chapters climb toward that picture in three stretches. Chapters 2 to 6 rebuild the station as it stands today on the new structure: value types, the display rule, a gauge shared between loops, the loops themselves, and a policy for failing and logging. Chapters 7 to 11 bring the network: build-time configuration, device names and topics, WiFi, a monitor that watches the link, and the clock. Chapters 12 to 14 put the broker on the other end.

Versions this book is checked against

Every API claim in this book is checked against the versions the project actually compiles, recorded in Cargo.lock and .cargo/config.toml. The project builds on ESP-IDF v6.1 since 2026-10-20, with esp-idf-svc 0.53.0, esp-idf-hal 0.47.0, and esp-idf-sys 0.38.1, all from crates.io. Those three crates used to live in separate repositories, which were archived into the esp-rs/esp-idf monorepo, and the project switched to their crates.io releases the same day.

The move to v6 changed one thing this book depends on. Since ESP-IDF v6.0, the MQTT C library (esp-mqtt) is no longer part of ESP-IDF, and it ships instead as the separate espressif/mqtt component with a version of its own. For example, the local v5.5.3 tree under ~/.espressif/esp-idf still has a components/mqtt directory, and the v6.1 tree has none, which is why Chapter 13 starts by adding espressif/mqtt 1.1.0 to Cargo.toml.

How a chapter works

Each chapter explains its concepts first and then hands over its plan task as the exercise, and the code in the repository is written by the reader. Tasks that touch fak-core are test-first: write the failing tests from the plan, watch cargo test-core fail to compile, implement, and watch it pass. Every task then goes through the gate, which is devenv test --no-tui, running cargo fmt, cargo test-core, clippy with warnings as errors (its pedantic lints, run separately with clippy-pedantic, are advice rather than part of the gate), and a release build, the same commands CI runs. After the gate come /code-review on the diff and the commit, with the message the plan gives.

Firmware tasks end on the board, since a percentage on the display or a message on the broker is the only proof that some of this code works. Code in a chapter that compiles but can only run on the hardware says so beside it, in a note that reads "compiled, not tested on the board", and the board check in the plan is where it gets tested. The questions each plan task lists (such as why run takes &mut self while display_loop takes only &dyn Gauge) appear in their chapters, answered after the reader has had a chance to try.
